daily-eks-practice - sealed answer key

Don't read this until you've tried the drill.

Every scenario below has the commands and the "why". The learning is in fumbling first - this file is for grading yourself afterwards, or for getting unstuck after a real attempt. Serve it with make serve-answers.

01 - Lay of the land

Nodes

kubectl get nodes -o wide
kubectl describe node <name> | grep -E 'instance-type|capacityType|zone|pods'
kubectl get node <name> -o jsonpath='{.status.allocatable.pods}'

Capacity type is the label eks.amazonaws.com/capacityType (SPOT here). Max pods on a t3.medium is 17 - it is an ENI/IP limit, not CPU/memory. That is why t3.small (11) is too tight for this stack.

Namespaces you should see

kube-system (cluster machinery + ALB controller), practice-app (the app + DB secret), argocd, monitoring, plus the default four.

App without any LB

kubectl -n practice-app port-forward svc/practice-app-frontend 8081:80
# browse http://localhost:8081

Reach RDS without a client

kubectl run tcpcheck --rm -it --restart=Never --image=busybox:1.36 -- \
  nc -zv -w 3 <rds-address> 5432

nc proves L4 reachability; no psql needed. The RDS address comes from make output.

02 - Scale the app

 
kubectl -n practice-app scale deploy practice-app-frontend --replicas=4
kubectl -n practice-app get pods -l app.kubernetes.io/component=frontend -o wide -w

If Argo CD manages the app, it now shows OutOfSync - git still says 2. That is the whole GitOps lesson: imperative changes are drift. The "right way" is editing frontend.replicas in values.yaml and letting the sync roll it.

Metrics + HPA

kubectl top pods -n practice-app
# values.yaml: hpa.enabled: true  ->  sync/deploy
kubectl -n practice-app get hpa -w

Load generation

kubectl run load --rm -it --restart=Never --image=busybox:1.36 -- \
  /bin/sh -c 'while true; do wget -q -O- http://practice-app-frontend.practice-app/ >/dev/null; done'

Who wins, replicas vs HPA? The HPA does - it owns scale and will fight any manual/values replica count between min and max. Best practice: remove replicas from the manifest once an HPA owns the workload (in helm, that means guarding it with if not .Values.hpa.enabled).

03 - Rolling update + rollback

 
kubectl -n practice-app rollout history deploy/practice-app-frontend
# bump values.yaml frontend.image.tag -> deploy, then:
kubectl -n practice-app rollout status deploy/practice-app-frontend
while true; do curl -so /dev/null -w '%{http_code}\n' localhost:8081; sleep .3; done

Default Deployment strategy: RollingUpdate with 25% maxSurge / 25% maxUnavailable. With readiness probes set, requests should not fail during the roll.

Rollback, both ways

kubectl -n practice-app rollout undo deploy/practice-app-frontend   # fast, imperative
git revert <commit> && git push                                     # the GitOps way

rollout undo in a GitOps shop is a trap: Argo CD will see drift and put the bad version back (especially with self-heal on). Git must be reverted for the rollback to stick.

Stuck rollout

With a bad tag you get ImagePullBackOff; the rollout waits forever on unready new pods while old pods keep serving (that is maxUnavailable protecting you). kubectl rollout undo or fix the tag.

04 - Load balancing

The controller runs in kube-system with an IRSA service account - kubectl -n kube-system get sa aws-load-balancer-controller -o yaml shows the eks.amazonaws.com/role-arn annotation. No node keys involved.

NLB (Service)

# values.yaml: frontend.service.type: LoadBalancer  -> deploy
kubectl -n practice-app get svc practice-app-frontend -w   # EXTERNAL-IP appears

The chart's annotations request external + ip targets: the NLB sends traffic straight to pod IPs (VPC CNI pods are first-class VPC citizens). instance mode would bounce through NodePorts instead.

ALB (Ingress)

# values.yaml: ingress.enabled: true -> deploy
kubectl -n practice-app get ingress -w                     # ADDRESS = ALB DNS name

Target group health checks hit each pod IP on the traffic port; scale to 0 and targets drain to zero - the ALB returns 503s.

Cleanup order matters: delete the Ingress/Service (controller deletes the AWS LB) BEFORE make down. Destroy the cluster first and the LB + its SGs orphan and keep billing, then block VPC deletion.

05 - DNS

 
kubectl run dnstest --rm -it --restart=Never --image=busybox:1.36 -- sh
/ # nslookup practice-app-backend.practice-app.svc.cluster.local
/ # cat /etc/resolv.conf

Short names work because resolv.conf carries search practice-app.svc.cluster.local svc.cluster.local cluster.local plus ndots:5. The nameserver IP (.10 of the service CIDR) belongs to the kube-dns Service in kube-system, which fronts the CoreDNS pods.

Corefile plugins: kubernetes answers cluster.local from the API, forward . /etc/resolv.conf sends everything else upstream (the VPC resolver, .2 of the VPC CIDR), cache keeps CoreDNS from melting. 

kubectl -n kube-system get configmap coredns -o yaml
kubectl -n kube-system scale deploy coredns --replicas=0   # break
kubectl -n kube-system scale deploy coredns --replicas=2   # fix

external-dns

Set the Ingress host under your zone; external-dns watches Ingresses and writes A/TXT records (the TXT is its ownership marker, tied to txtOwnerId). Policy sync deletes records when the Ingress goes; upsert-only would leave them.

06 - Storage

EBS

kubectl get storageclass                       # gp2 (in-tree default) - make a gp3 one
kubectl apply -f - <<'EOF'
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata: { name: gp3 }
provisioner: ebs.csi.aws.com
parameters: { type: gp3 }
volumeBindingMode: WaitForFirstConsumer
allowVolumeExpansion: true
EOF

WaitForFirstConsumer delays provisioning until a pod schedules, so the volume lands in the pod's AZ (EBS is AZ-locked). allowVolumeExpansion is what makes the live resize possible; edit spec.resources.requests.storage on the PVC and the CSI driver grows volume + filesystem.

The volume in the console carries kubernetes.io/created-for/pvc/name tags plus this repo's Project/Environment tags. Reclaim policy Delete removes it with the PVC.

S3 via IRSA

kubectl -n practice-app run s3test --rm -it --restart=Never \
  --overrides='{"spec":{"serviceAccountName":"s3-explorer"}}' \
  --image=amazon/aws-cli -- s3 ls s3://$(make output 2>/dev/null | grep -o 'daily-eks-practice[^"]*practice[^"]*' | head -1)

Credential chain: the SA's role-arn annotation makes EKS inject a projected OIDC token file + env vars; the SDK calls AssumeRoleWithWebIdentity; STS trusts the token because the cluster's OIDC provider is registered in IAM, scoped to exactly system:serviceaccount:practice-app:s3-explorer. Without the SA there are no credentials at all - the CLI errors immediately.

07 - Prometheus + Grafana

 
make grafana-ui                                # admin / (make output -> grafana_admin_password)
kubectl -n monitoring port-forward svc/monitoring-kube-prometheus-prometheus 9090:9090

The kube_* metrics come from kube-state-metrics (object states from the API), while container_* comes from cAdvisor in each kubelet, and node_* from node-exporter. Three different exporters, one scrape config. 

# the three from the card:
rate(container_cpu_usage_seconds_total{namespace="practice-app"}[5m])
kube_pod_container_status_restarts_total{namespace="practice-app"}
kube_deployment_status_replicas_available{deployment=~".*frontend"}

Alert idea: kube_deployment_status_replicas_available{deployment=~".*frontend"} < 2 for 2m. Trip it by scaling to 1.

08 - CloudWatch

 
# config.toml: enabled_cluster_log_types = ["api", "audit"]  -> make apply
aws logs describe-log-groups --log-group-name-prefix /aws/eks/
aws logs put-retention-policy --log-group-name /aws/eks/<cluster>/cluster --retention-in-days 1

Logs Insights, audit stream: filter { $.user.username = "kubernetes-admin" && $.verb = "create" } (or your role name). Every kubectl you run is in there.

Container Insights: add amazon-cloudwatch-observability to managed_addons. The agent pods will crash on permissions until the node role has CloudWatchAgentServerPolicy - the pod logs say exactly that. (Attach it via terraform on the node role; that is the exercise.)

When to pay for it: when your org's alerting/on-call tooling lives in CloudWatch, when you need logs+metrics correlated per pod without running your own stack, or for control-plane visibility Prometheus cannot see. Otherwise scenario 07's stack is free-er.

Turn it all back off the same day - audit ingestion is the classic surprise line item.

09 - GitOps with Argo CD

 
make argo-ui        # admin + printed password
# creds live here after repo registration:
kubectl -n argocd get secret -l argocd.argoproj.io/secret-type=repository

Register the private repo (fine-grained PAT, contents read-only): UI → Settings → Repositories → HTTPS, or argocd repo add https://github.com/<you>/daily-eks-practice.git --username git --password <PAT>. The PAT ends up in that namespaced Secret - in your cluster, never in git. 

make app-deploy
kubectl -n argocd get application practice-app -w

Drift drill: after the manual scale, the app shows OutOfSync with a live/target diff on spec.replicas. Auto-sync + self-heal (Application spec): 

spec:
  syncPolicy:
    automated: { prune: true, selfHeal: true }

With self-heal on, Argo reverts manual kubectl changes within seconds - which is also why rollout undo stopped working for you in scenario 03.

10 - Break/fix signatures
  • CrashLoopBackOff: container starts then dies; kubectl logs --previous has the real error (PostgREST: connection refused/auth failed).
  • Bad readiness probe: rollout stuck at "1 old / 1 new"; new pod Running but 0/1 Ready; events show probe 404s. Old pods keep serving - that's maxUnavailable doing its job.
  • ImagePullBackOff: kubelet on the node reports it; describe pod events show the registry 404/manifest unknown.
  • OOMKilled: describe pod → lastState.terminated.reason: OOMKilled, exit code 137. Restarts climb.
  • Pending: scheduler event says it verbatim: "0/2 nodes are available: 2 Insufficient cpu."
  • cordon vs drain: cordon only marks unschedulable (running pods stay); drain evicts respecting PDBs. Deleted pods reschedule to other nodes because the ReplicaSet, not the node, owns them.
  • Selector typo: pods Ready, service up, app dead. kubectl get endpoints shows an empty endpoints list - the smoking gun for selector/label mismatch.

11 - RDS day-2

Laptop connect fails because (1) publicly_accessible = false - no public IP/DNS resolution outside the VPC, and (2) the DB security group only allows 5432 from the EKS cluster security group (a SG reference, not a CIDR - that's the answer to task 3). 

kubectl -n practice-app run psql --rm -it --restart=Never --image=postgres:16-alpine \
  --env="PGPASSWORD=$(kubectl -n practice-app get secret practice-db -o jsonpath='{.data.password}' | base64 -d)" -- \
  psql -h <address> -U practice_admin -d practice

Rotation order

  1. Change the master password in RDS (finishes in seconds, old connections survive).
  2. Update the k8s secret (kubectl -n practice-app edit secret practice-db - remember db-uri holds it too).
  3. kubectl -n practice-app rollout restart deploy practice-app-backend.

Backwards = the backend restarts with the old password and crashloops on auth until RDS catches up. Terraform drift: make plan wants to set the password back to the one in state (random_password). Here that is harmless-ish; in prod it is exactly why passwords managed outside terraform should use manage_master_user_password / Secrets Manager instead.

Cost trades vs prod: single-AZ (no failover), backup_retention_period = 0 (no PITR!), tiny instance, no deletion protection, no performance insights. Every one of those flips for a real database.

12 - CI via OIDC

 
AWS_PROFILE=<admin> python3 scripts/bootstrap.py bootstrap-oidc init -input=false
AWS_PROFILE=<admin> python3 scripts/bootstrap.py bootstrap-oidc apply
gh variable set AWS_ROLE_ARN --body "$(python3 scripts/bootstrap.py bootstrap-oidc output -raw role_arn)"
gh secret set CONFIG_TOML < scripts/config.toml

The handshake in three sentences: GitHub mints a short-lived OIDC token for the workflow run, signed by token.actions.githubusercontent.com and carrying a sub claim like repo:you/daily-eks-practice:ref:refs/heads/main. The workflow calls STS AssumeRoleWithWebIdentity with that token. STS checks the role's trust policy - which trusts that issuer and that exact repo pattern - and returns temporary credentials; no stored keys anywhere.

Tightening for a real org: set subject_claims to specific branches/environments (e.g. repo:org/repo:environment:dev) and swap AdministratorAccess for a scoped policy. The gated apply comes from the environment: dev line in the workflow + required reviewers on that environment.
